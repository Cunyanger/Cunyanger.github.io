# 《敏捷软件开发：原则、模式与实践》

Robert C. Martin 的《敏捷软件开发：原则、模式与实践》不是一本只讲敏捷流程的书。它真正想讲的是：

```text
敏捷不是少写文档、少做设计，而是用反馈驱动开发，并让代码结构足够适应变化。
```

这本书由三条线组成：

- 敏捷开发实践：迭代、测试、重构、结对、持续反馈。
- 面向对象设计原则：SOLID 是核心。
- 设计模式与案例：用模式解决依赖、扩展、复用和变化问题。

## 适合谁读

- 已经会 Java，但代码经常越改越乱的开发者。
- 想系统理解 SOLID 原则的人。
- 想把设计模式用到真实业务，而不是背概念的人。
- 技术负责人、架构师、需要带团队做迭代交付的人。

## 阅读路线

1. 先读敏捷实践部分，理解反馈和迭代。
2. 重点读 SOLID 五大原则。
3. 设计模式部分按“解决什么变化”来读。
4. 案例部分重点看如何把原则落到代码结构。

## 第一部分 敏捷开发

### 第 1 章 敏捷实践

敏捷的核心不是流程仪式，而是快速反馈。通过短迭代、持续集成、测试、客户参与和频繁交付，尽早发现需求和设计问题。

重点：

- 需求会变化，流程必须接受变化。
- 软件只有持续交付，才能持续校准方向。
- 团队协作比厚重流程更重要。
- 可工作的软件比静态文档更能验证真实进展。

### 第 2 章 极限编程概览

极限编程强调一组相互支撑的实践：结对编程、测试先行、持续集成、小版本发布、简单设计、重构、集体代码所有权。

重点：

- 单个实践效果有限，组合起来才稳定。
- 测试让重构有底气。
- 小版本发布让反馈周期变短。
- 简单设计不是不设计，而是不为未知未来过度设计。

### 第 3 章 计划

敏捷计划不是一次性制定长期固定计划，而是持续调整。用户故事、估算、优先级和迭代计划共同构成节奏。

重点：

- 计划是为了帮助决策，不是为了假装未来不会变。
- 估算应基于历史速度持续修正。
- 需求优先级由业务价值驱动。
- 每次迭代都应该交付可验证的软件。

### 第 4 章 测试

测试是敏捷开发的安全网。单元测试帮助开发者确认设计和行为，验收测试帮助确认业务需求。

重点：

- 测试不是 QA 的独立责任。
- 测试越靠近开发越便宜。
- 单测能促进低耦合设计。
- 没有测试，重构会变成赌博。

### 第 5 章 重构

重构是在不改变外部行为的前提下改善内部结构。敏捷开发依赖重构，因为需求会变化，设计需要持续演进。

重点：

- 重构必须有测试保护。
- 重构是小步持续改进，不是大规模推倒重来。
- 坏味道包括重复代码、长函数、巨大类、依赖混乱。
- 代码结构越清晰，后续迭代越快。

### 第 6 章 编程实践片段

本章通过一个编程过程展示测试、重构和设计演进如何结合。重点不是最终代码，而是每一步如何通过反馈做决策。

重点：

- 不要试图一次设计完美。
- 先让测试表达需求。
- 再让代码通过测试。
- 最后通过重构改善结构。

## 第二部分 敏捷设计原则

### 第 7 章 什么是敏捷设计

敏捷设计不是预先画大量图，而是让设计始终保持可变、可测、可理解。坏设计的典型特征是僵化、脆弱、不可复用和粘滞。

重点：

- 僵化：一个小改动牵动很多地方。
- 脆弱：修改一处，其他地方莫名坏掉。
- 不可复用：模块依赖太多，无法拿出来用。
- 粘滞：正确做法比错误做法更难。

### 第 8 章 单一职责原则 SRP

一个类应该只有一个引起它变化的原因。职责不是方法数量，而是变化原因。

重点：

- 用户管理、权限校验、报表导出不应混在一个类里。
- 一个类承担多个角色时，变化会互相影响。
- 拆分职责能降低修改范围。

### 第 9 章 开闭原则 OCP

软件实体应该对扩展开放，对修改关闭。新增行为时尽量通过新增代码完成，而不是频繁改已有稳定代码。

重点：

- 抽象和多态是实现开闭原则的重要手段。
- Strategy、Template Method、Factory 都服务于扩展点设计。
- 不要为所有地方提前抽象，只在变化真实出现时抽象。

### 第 10 章 里氏替换原则 LSP

子类型必须能够替换父类型，并保持程序正确性。继承不是代码复用工具，而是行为契约。

重点：

- 子类不能破坏父类承诺。
- “是一个”的继承关系必须符合行为语义。
- 违反 LSP 常导致大量 `if instanceOf` 和特殊判断。

### 第 11 章 依赖倒置原则 DIP

高层策略不应该依赖低层细节，二者都应该依赖抽象。抽象不应该依赖细节，细节应该依赖抽象。

重点：

- Service 不应该直接依赖具体第三方 SDK。
- 业务核心定义接口，基础设施实现接口。
- Spring 的依赖注入是落地 DIP 的常用方式。

### 第 12 章 接口隔离原则 ISP

客户端不应该依赖它不使用的方法。大而全接口会迫使实现类依赖无关能力。

重点：

- 拆成小接口能减少无关依赖。
- 不要设计万能 Service 接口。
- 接口应该按使用方需求划分，而不是按实现类方便划分。

## 第三部分 常见设计模式

### Command 与 Active Object

Command 把请求封装成对象，使请求可以排队、记录、撤销或异步执行。Active Object 进一步把调用和执行线程解耦。

适用场景：

- 任务队列。
- 异步命令。
- 操作日志。
- 可撤销操作。

### Template Method 与 Strategy

Template Method 通过继承固定算法骨架，把可变步骤交给子类。Strategy 通过组合替换算法。

重点：

- Template Method 更偏继承复用。
- Strategy 更偏运行时替换。
- 现代 Java 项目中，组合通常比继承更灵活。

### Facade 与 Mediator

Facade 为复杂子系统提供简单入口。Mediator 用中介对象协调多个对象之间的交互，降低对象间直接依赖。

适用场景：

- 对外暴露简化 API。
- 聚合多个内部服务调用。
- 降低多个组件之间的网状依赖。

### Singleton 与 Monostate

Singleton 保证一个类只有一个实例。Monostate 让多个实例共享同一状态。

注意：

- 单例容易隐藏全局状态。
- 单例会降低测试隔离性。
- Spring Bean 默认单例，但不等于所有对象都该做成单例。

### Null Object

Null Object 用一个“什么都不做”的对象代替 `null`，避免调用方到处判空。

适用场景：

- 可选策略。
- 默认行为。
- 空权限、空通知、空日志实现。

### Factory

Factory 封装对象创建逻辑，把“使用对象”和“创建对象”分开。

适用场景：

- 根据类型创建不同实现。
- 创建过程复杂。
- 调用方不应依赖具体类。

### Composite

Composite 用树形结构表示整体和部分，让调用方用统一方式处理单个对象和组合对象。

适用场景：

- 菜单树。
- 组织架构。
- 文件目录。
- 权限树。

### Observer

Observer 让对象状态变化时通知多个观察者，实现发布订阅式解耦。

适用场景：

- 事件通知。
- Spring ApplicationEvent。
- 领域事件。
- UI 状态更新。

### Adapter、Bridge、Proxy

Adapter 用于接口适配，Bridge 用于抽象和实现分离，Proxy 用于控制对象访问。

在 Java 后端中常见落地：

- Adapter：适配第三方支付接口。
- Bridge：不同消息渠道和不同消息内容解耦。
- Proxy：AOP、事务、缓存、权限代理。

### Visitor 与 State

Visitor 把操作从对象结构中分离出来，适合对象结构稳定、操作经常变化的场景。State 把状态相关行为封装到状态对象中，适合状态流转复杂的业务。

适用场景：

- Visitor：AST、规则检查、报表导出。
- State：订单状态、工单状态、审批流。

## 第四部分 案例和包设计

书中的 Payroll 等案例展示了一个重点：设计不是先画完类图再编码，而是在需求、测试和重构中不断浮现。

包设计原则可以概括为：

- 共同复用原则：经常一起复用的类放在一起。
- 共同闭包原则：经常一起变化的类放在一起。
- 无环依赖原则：包之间不要形成循环依赖。
- 稳定依赖原则：不稳定模块依赖稳定模块。
- 稳定抽象原则：越稳定的模块越应该抽象。

## 在 Spring Boot 项目中的落地

### Service 层

- 用 SRP 拆分应用服务、领域服务和基础设施服务。
- 用 DIP 隔离第三方 SDK、MQ、Redis、文件存储。
- 用 Strategy 处理不同业务算法。
- 用 State 管理复杂状态流转。

### Controller 层

- 只做 HTTP 入参、校验和响应转换。
- 不写业务规则。
- 不直接操作数据库。

### Repository 层

- 用接口隔离业务与持久化细节。
- Mapper、JPA、第三方查询都放在基础设施层。

### 测试

- 核心业务规则先写单元测试。
- 重构前补测试。
- 外部依赖用 Mock 或测试容器隔离。

## 速记

| 概念 | 一句话理解 |
| --- | --- |
| 敏捷 | 用短反馈持续校准方向 |
| TDD | 用测试定义行为并保护重构 |
| 重构 | 不改行为，改善结构 |
| SRP | 一个类只有一个变化原因 |
| OCP | 新需求尽量靠扩展实现 |
| LSP | 子类必须遵守父类契约 |
| DIP | 高层策略依赖抽象，不依赖细节 |
| ISP | 接口要小，按客户端需求拆 |
| 模式 | 为变化点提供稳定结构 |

## 总结

这本书的核心不是“背敏捷术语”或“背设计模式”，而是理解变化如何影响代码结构。

```text
敏捷靠反馈，不靠口号。
好设计靠原则，不靠感觉。
设计模式是应对变化的工具，不是炫技模板。
```
